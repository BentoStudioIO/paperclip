# Plan: Shared Agent Workspace VPS (OVH BHS) — consolidated

Synthesized from 5 parallel planning agents (2026-06-09): provisioning/hardening, tool inventory, credentials/access, monitoring/security, execution-layer/Dokploy. Supersedes the Daytona-on-QA execution plane (CTO override, new evidence: Daytona = 8-svc overhead + sync-hangs + double-wake races for a use case needing no container isolation).

## Target box
OVH **VPS-1 2026**, 4 vCPU / 8 GB / 75 GB NVMe, Ubuntu 24.04, BHS (Canada — same region as the fleet). DNS `agents.bentostudio.io` (cfdns, proxied:false). Purpose: shared workspace where Paperclip AI agents develop Pharmia AND humans operate the fleet. **No Daytona. No Dokploy.**

## Cross-cutting principles (emerged from all 5 axes)
1. **Tool presence ≠ credential grant.** Install EVERY tool on the box; grant prod-capable creds **per-identity**, not per-box.
2. **Two OS identities, OS-isolated:** `agent` (Paperclip's ssh target — capped: dev/qa rw, prod READ-only, comp rw, no sudo, no prod SSH key, no cfdns/ovh/dokploy-prod write) vs `human-ops` (full prod creds). The boundary is filesystem perms + sudo policy + separate SSH principals, not just different env values.
3. **No fleet host-monitoring plane exists** — the LGTM stack is per-env *app* telemetry, internal-only. The only fleet-wide host agent is **Wazuh**. This box's host security+health lives in Wazuh, not Grafana.
4. **The double-wake bug is Paperclip control-plane, driver-agnostic** — Daytona masked it; it WILL recur on ssh. Fixing it (atomic run-claim) is the highest-leverage item, independent of the box.
5. **"Agent prod read-only" is illusory today** — `pg` reaches prod via `ssh prod sudo docker exec -U postgres`; the RO Postgres role from the locked plan was never built. Agents get ZERO prod-DB until it exists.
6. **Prod access is APPROVAL-GATED, not blanket-denied (CTO, 2026-06-09).** Agents get prod READS ungated (RO role), and prod WRITES **via human-approved gates** (Discord/Slack embed → approve/reject → execute). The robust shape is a **privileged broker**: the `agent` identity holds NO prod-write creds; an agent prod action raises a Paperclip approval → Discord embed → human approves → a separate privileged process (holding the creds) executes and returns the result. No click ⇒ no prod write, even if the agent is compromised. Paperclip's Discord/Slack plugins already provide the approval-embed UX (currently DISABLED — they flooded because installed-but-unconfigured; configure+re-enable for the gate). Detailed design: separate approval-gate planner (in flight) + this revises the credentials axis: agent = dev/qa rw + prod read + prod-write-via-approval-broker, NO direct prod creds.

## DECISIONS NEEDED (forks)
- **D1 — Topology.** Recommended: **dual-identity box** (`agent` capped + `human-ops` full, OS-isolated) — satisfies "every tool to access prod" (human) + "agents run here" (capped). Residual risk: OS-boundary failure (kernel LPE) → full compromise; mitigated by non-sudo agent + Wazuh/auditd. Alternative: agent-only box, humans keep prod ops on existing paths (lower blast radius, but loses the "one shared prod-ops workspace" goal).
- **D2 — RO Postgres role.** Recommended: **build it now** (`pharmia_readonly`, SELECT-only, non-sudo connection path) so agents can read canary DB safely. Until then agents get no prod-DB. (Law-25 parked: RO role sees unredacted PHI; keep LLM on ZDR model.)
- **D3 — Double-wake fix.** Recommended: atomic claim (Postgres advisory lock or conditional `UPDATE ... WHERE status='queued'`) + `maxConcurrentRuns=1` per agent + a box-level concurrency cap (OOM guard on 8 GB). File/fix upstream in Paperclip.
- **D4 — Confirmations:** non-root `agentops` operator + root SSH disabled (Y); `agents.bentostudio.io` (Y); LUKS before secrets land (Y); no Dokploy (Y); Daytona teardown (Y, the override).

## Approval-gated prod access (design — axis 6)
**Native primitive exists — don't build it.** Paperclip has a complete agent-initiated, board-gated approval flow: agent calls MCP `paperclipCreateApproval` (`type:request_board_approval`, `payload.kind:prod_action` — no schema change) → `approval.created` event → status pending; decisions (`/approve` etc.) are `assertBoard`-gated (humans only, never agents); **`/approve` wakes the requesting agent** with the decision (`server/src/routes/approvals.ts:182-205`). Agent "blocks" by ending its turn; approval re-wakes it. Reject = silent (no wakeup) → recommend a small upstream wake-on-reject (D-A4).

**Discord = the gate UX.** Re-enable + **configure** the discord plugin: `discordBotTokenRef`, `defaultChannelId`, `approvalsChannelId` (private, approver-only), `enableEscalations`, `paperclipBoardApiKeyRef` (board-scoped key the plugin uses to call `/approve` on a button click). Flow: `approval.created` → plugin posts embed w/ Approve/Reject buttons → human clicks → plugin verifies Discord Ed25519 signature + approver allow-list → calls `/approvals/:id/approve` as board actor → agent wakes. **Flood:** root cause is the scheduler dispatching every `active` plugin_jobs row gated only on worker-running, NOT config (`plugin-job-scheduler.ts:263-319`). Configuring makes the jobs *succeed* (fixes the error-flood) + arms approvals; raw 1-row/job/tick volume persists by design → trim cron cadence as follow-up. NOT a host bug. **Slack** later (parity).

**Privileged broker (correctness-by-construction).** A dedicated **`prod-broker`** identity (own user; recommend standalone systemd on the agent VPS, off the Paperclip host) is the SOLE holder of prod-write creds. It subscribes to approved approvals, re-validates the row server-side + re-checks the policy matrix + executes (via the existing prod wrapper CLIs, as broker not agent) + writes result back to the run (approval/issue comment, read on the agent's wakeup) + audits → Wazuh. Agent holds NO prod cred and has no code path to the broker except an approval a human must approve ⇒ no-click-no-prod-write is unrepresentable.

**Policy matrix (enforced twice: agent cred-scoping + broker re-check):** ALLOWED ungated = all prod reads (RO Postgres D2, loki/prom canary Viewer, comp/twenty read). GATED = prod-DB writes, `cfdns` prod DNS, `dokploy` prod/canary deploy (complements the husky CONFIRM hook which guards the *git-push* path; the gate guards the *agent-CLI* path), `pharmia-tenant` prod, `comp` publish. HARD-DENY even with approval = `ovhcloud` VPS delete/rebuild, prod DB DROP/DDL/migrations, secret exfiltration, identity/cred mutation. Default (not in table) ⇒ HARD-DENY.

**Pre-build gate (R1):** the discord/slack plugins are EXTERNAL npm packages (not in repo) — before building the broker against them, read the live installed plugin source (`ssh bento` + the install dir, or `GET /api/plugins`) to confirm it subscribes to `approval.created` and implements signed-webhook interactivity. If not, a small plugin-side patch is needed.

**Approval-gate decisions (D-A1..6):** dedicated `prod-broker` user (rec) · standalone systemd broker on the agent VPS (rec) · reuse `request_board_approval`+`payload.kind` no upstream enum (rec) · contribute upstream wake-on-reject (rec) · configure-now + trim cron cadence later (rec) · Discord-only v1 (rec).

This REVISES Phase 3: agent = dev/qa rw + prod read + **prod-write only via the approval broker**; agent still holds zero prod-write cred. Strengthens, not loosens, the locked model.

## Remote dev + CDE-platform evaluation (Coder / E2B / alternatives — 2026-06-09)
Two independent deep-dives (Coder in-depth + alternatives scan, current sources, Coder v2.33.7). **Verdict: no platform beats the lean ssh-driver on this 4c/8GB box. Add `code-server` only.**
- **Coder = SKIP (for this box).** (1) Control-plane tax ~1.5 GB (coderd + Postgres + provisionerd) on an 8 GB box already at OOM risk (R6) — strictly worse; comfortable Coder wants ~8c/16GB+ + external PG. (2) **Duplicates Paperclip's orchestration** — Coder Tasks/Agents is *its own* agent loop, not your Paperclip agents w/ skills + gated-prod broker; you'd disable its headline feature. (3) The single-host `docker` template **mounts /var/run/docker.sock into workspaces = host-root**, breaking the non-sudo/dual-identity isolation the plan depends on (mitigated only by the PAID Agent Firewall). (4) Wildcard-domain reverse proxy (same pain as Daytona's toolbox) vs ufw default-deny + cfdns proxied:false. (5) The genuinely novel bits (control-plane agent loop, AI Gateway central key mgmt, Agent Firewall) are **paid** + run Coder's agent not ours. **Revisit ONLY on a bigger box (~8c/16GB+) as a governed multi-dev *human* IDE (OIDC via PocketID) — never as the agent execution plane.**
- **emdash / mux / DevPod = SKIP** — laptop-side desktop apps that SSH into a box (the role Paperclip already fills); adopting one splits the orchestration brain, doesn't "leverage the box."
- **E2B = escape hatch, NOT self-host.** E2B self-host is Terraform GCP/AWS-only (can't run on OVH). But Paperclip ALREADY ships `e2b`/`modal`/`cloudflare`/`exe-dev` sandbox-provider plugins → if per-run isolation ever needs to exceed OS-user+worktree (untrusted-code blast radius), it's a **config flip to managed E2B**, no build, no box footprint. (Data leaves the box — fine for dev/qa code, mind ZDR for anything clinical.)
- **DECISION — how the box is "leveraged for agents":** it already IS the agent platform — Paperclip ssh-driver runs agents there in per-run worktrees with the full toolkit + gated-prod broker. The one additive piece: **`code-server`** (browser VS Code, ~1 binary, scoped to `human-ops`, behind Cloudflare + box auth) OR plain **VS Code Remote-SSH / JetBrains Gateway** over the existing SSH principal — zero added platform. Add to Phase 2.
