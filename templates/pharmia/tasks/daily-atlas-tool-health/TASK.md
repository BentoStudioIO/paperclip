Run the DAILY ATLAS HEALTH CHECK now, autonomously, against the canary environment. Use the atlas-rca and atlas-render-regression skills.

## Steps

1. **Start from user satisfaction (do this FIRST — it is the most direct quality signal).** Run `threads chains canary --since 24h` and actually READ the question chains. This dumps every thread's user turns verbatim, in order, and folds in explicit `atlas_message_reaction` dislikes (marked `[DISLIKE]`). You are the judge — there is no regex verdict: scan each multi-turn chain for a follow-up that re-asks the same thing, demands a source/reference, pushes back ("une méta analyse ??", "jai besoin d'une meilleure reference", "c'est faux", "es-tu sûr"), or abandons the topic unsatisfied. Those mean the prior answer missed. (Dislikes are rare, ~single-digits/month — run `--since 7d` periodically to sweep them; cross-check yesterday's `~/.cache/pharmia-health/atlas-*.md` and SKIP chains already actioned.) For each chain that reads as dissatisfaction, open it (`threads canary <thread-id> --rca`, or paste the URL) and run the atlas-rca attribution tree to find WHY: a source/reference-demand chain is usually a citation/coverage gap (→ Step 5/6); a "not what I asked" is a routing/comprehension miss (→ model/prompt); a wrong-fact pushback ("c'est faux …") is a fabrication or stale-corpus issue; any URL a user flagged as wrong/dead → feed straight into Step 6's URL-validation + corpus-linkcheck. Feed every dissatisfaction finding into the same root-cause + remediation machinery as the rest of the run; never leave one un-triaged.
2. Run `threads modelmix canary --since 24h` for the fleet model/fallback picture.
3. Sample a handful of recent canary Atlas threads via the `threads` CLI and inspect them for: unrendered markup/tags, fabricated or uncited clinical data, and tool failures (esp. getDrugShortages 401-on-stale-token, searchPubmed hard-empty, readUrls junk/403 passthrough, healthCanadaSearch empty). (`threads <url>` handles compound ids fine; if it returns no rows for a very fresh thread it is a flush race — retry, or fall back to `pg canary mastra` on `mastra_messages` filtering `thread_id like '<uuid>%'`).
3. Confirm external clinical tools return the expected shape.
4. **Capability-gap / missing-info detection.** Find turns where Atlas struggled to find the answer: high tool-call counts in a single turn, repeated or low-yield retrieval, and especially webSearch used multiple times as a fallback (a tell that the dedicated clinical tools could not supply the answer — e.g. one real turn fired 5× webSearch + 3× readUrls + 2× searchPubmed = 17 tool calls). For each, diagnose WHAT information was being sought and WHY the existing tools did not supply it, then distinguish: (a) a genuine COVERAGE gap — no tool can answer it → propose a concrete capability upgrade (a new tool, a new/expanded data source or index, a catalog/dedup addition); vs (b) a ROUTING miss — a capable tool exists but was not chosen → propose a prompt/routing fix. Quantify each finding (tool, count, what was sought).
5. **Generated-source URL validation.** For the sampled threads, extract every URL Atlas emitted in its `<pharmia-source>` citations and check each resolves: `curl -sL -o /dev/null -w '%{http_code}' "<url>"` — treat any 4xx/5xx as dead (a real example: a cited `pharmacists.ca/.../compendium-of-therapeutic-choices/` returned 500). For each dead URL, TRACE its provenance and fix the right layer: (a) it is the canonical URL of an Outline doc / clinical reference (find it via `ol search` and the listClinicalReferences/readClinicalReferences tools) → the Outline SOURCE holds a stale URL: action item = correct the URL in the Outline doc, and run `ol linkcheck --collection 50a7902d-439f-479a-9469-43926a4206a5 --json` (the Quebec Documents collection) to find every sibling dead URL across the corpus at the source, so the whole class is fixed at once, not whack-a-moled per thread; (b) readUrls/webSearch passed a broken link straight through → readUrls/grounding fix; (c) the model constructed an unverified URL → citation-contract fix (never emit an unverified URL). Cite the dead URL + its HTTP status + the doc/tool it came from. **Standing corpus check (run every time, not only when a thread surfaces a dead link):** run `ol linkcheck --collection 50a7902d-439f-479a-9469-43926a4206a5 --json` (slow over 540 docs — launch it in the background early in the run and read it near the end). TRIAGE BY STATUS — most flags are anti-bot FALSE POSITIVES, do NOT edit docs for them: `403`/`401`/`429` and any `3xx→000` (redirect-then-000, e.g. doi.org / gc.ca / publishers) are live-behind-a-bot — re-verify a sample with `curl -sL -A 'Mozilla/5.0'` or `curl_cffi impersonate='chrome136'` before believing any single one is dead. Only `404`, `500`, `410`, and hard `000` (no redirect) are REAL dead. Fix every real-dead URL AT THE OUTLINE SOURCE: `ol doc get <id> --raw > /tmp/f.md`, atomic python replace (count-verified — Edit tool races on /tmp), `ol doc update <id> --file /tmp/f.md --no-link-check`; verify the replacement resolves 200 and re-fetch shows 0 dead-pattern lines. When a dead URL has no verified live equivalent, DROP the link (keep the citation text, remove the URL) rather than pointing it at a generic landing. Group identical dead URLs into one class and fix all sibling docs in one pass.

## For every issue

Do NOT stop at detection — investigate the ROOT CAUSE directly: pull the raw turn with `threads <id> --rca` / `--tools` / `--json`, identify the failing layer per atlas-rca (tool / model / render / persistence / coverage), and confirm the mechanism (e.g. an Outline 404, a hallucinated id/cite, an invalid mermaid type, a missing data source). GROUP findings that share one root cause. For each group propose a CONCRETE action item: owner skill/file + the fix + how to validate (an eval scenario, or a failing→green repro in `tooling/`). Cheaply validate a proposed fix when you can (e.g. run `mermaid.parse` from repo root). Render fixes must name a repro harness per atlas-render-regression; model/prompt fixes must route through model-config-gate.

## Remediation policy

- **Proactive — fix in-run, no approval (docs + tooling ONLY):** Outline / clinical-corpus docs (URL rot, stale refs), CLI scripts in `~/.local/bin`, paperclip task/skill SSOT, dashboard/config files. Fix at the source, verify (200 / re-fetch / re-run), list under **Remediated**. These are low-risk and reversible.
- **Ask first — propose, do NOT ship (anything in the Pharmia repo):** `PharmaMate` apps/packages/tooling, agent prompts, model/routing config, evals, render menders. Back it with a failing→green repro or eval, list it under **Needs approval**, and stop. NEVER push a Pharmia branch or open a PR from this task.

## Output — terse, one line per item (no prose paragraphs; omit empty sections)

Write `~/.cache/pharmia-health/atlas-$(date +%F).md` in this exact shape:
- **Header:** `# Atlas Health <date> — <GREEN | N issue(s)>`
- **Four one-liners:** `Satisfaction:` chains read · how many read as dissatisfaction · the dominant kind (source-demand|not-what-asked|wrong-fact|abandon) — or `ok`. `Fleet:` provider mix · fallback% · flips (benign?). `Signals:` tools · render · citations · URLs — each `ok` or a count. `Capability:` `none`, or `tool×count: what was sought → coverage|routing`.
- **`## Issues`** (omit if none) — one bullet each: `[tool|model|render|persist|coverage] <symptom> — RC <root cause>. → REMEDIATED <doc/cli> | ASK <pharmia file>`
- **`## Remediated`** (docs/CLI/Outline fixed this run) — one bullet each: `<doc-id|cli|url>: <what> (verified <how>)`
- **`## Needs approval`** (Pharmia repo — proposed, not shipped) — one bullet each: `<file>: <fix> — validate <repro/eval>`

Then PushNotification, one line: `Atlas <date>: GREEN` — or `Atlas <date>: N issues, k remediated, j need approval — <worst one-liner>`.
